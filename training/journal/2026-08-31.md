# 2026-08-31 — Harness no-output repair

Investigated DeepSeek Harness showing no response from the temporary Phase 6
API. Server logs showed that requests eventually completed with HTTP 200, so
the model was not completely stalled. The actual failure was an integration
queue/streaming problem: title generation and the real answer competed for one
MLX worker, while the API did not start its SSE response until inference had
already completed. Harness timed out and retried before seeing any bytes.

Patched and restarted the remote API without replacing model weights or the
active adapter. Title generation is now deterministic and does not use MLX.
The answer route immediately opens SSE and emits five-second keep-alive
comments until inference completes.

Measured results:

- Title: correct content; TTFB 1.735 ms; total 1.969 ms.
- Model answer: TTFB 2.478 ms; total 11.604 s; two keep-alives; final content
  and `[DONE]` received.
- Existing MacBook-to-mini tunnel remained healthy.

Negative result retained: the sampled Phase 6 answer appended an unwanted
format instruction after its substantive answer. This is not a transport
failure and must not be hidden by claiming Phase 6 is deployment-ready. The
adapter remains a temporary Harness test candidate pending model-quality work.

See `training/patches/harness-sse-timeout-fix.md` for deployment paths, hash,
recovery, and complete regression evidence.

## Live Harness regression after transport repair

Ran three visible turns in a fresh Harness conversation. All requests returned,
confirming the no-output transport defect is fixed. Semantic pass rate was 0/3:
two legitimate evidence-boundary questions were incorrectly replaced by the
same no-tool canned response, and a neutral 500/502/504 comparison returned
only a training-format instruction after roughly 14 seconds. Phase 6 therefore
remains deployment-blocked. Full prompts and observations are recorded in
`training/eval/phase6-harness-live-regression-2026-08-31.md`.

## Layer ablation diagnosis

Ran the same 500/502/504 question through the base model, LoRA, worker prompt,
fresh API, and contaminated-history API. Base Qwen, Phase 6 LoRA under standard
Qwen ChatML, current worker prompt, and a fresh API conversation all produced
substantive answers. Replaying the two erroneous evidence-gate assistant replies
before the same question produced an empty answer, matching the Harness failure
class. This proves the base model was not trained out of normal conversation;
the over-broad gate creates poisoned history that suppresses later generation.
Also discovered that the local tokenizer lacks a configured `chat_template`.
See `training/eval/phase6-layer-ablation-report-2026-08-31.md`.

## Gate/ChatML/history repair

Narrowed the execution-claim gate, switched the worker to explicit Qwen ChatML,
and removed only exact legacy canned gate exchanges before inference. During
deployment, found that the API silently ignores command-line `--port`, `--model`,
and `--adapter`; the correctly tested service was restarted with environment
variables on port 18766. Direct regression covered a legitimate analysis prompt,
a true execution-claim gate case, contaminated history recovery, and a simulated
read-only screenshot tool call. All passed. Two fresh visible Harness turns also
returned substantive answers without empty output or template leakage.

Negative results remain: 502 was mislabeled as a timeout in one answer, an early
answer over-inferred from intermittency, response latency was roughly 22–37 s,
and output is still delivered as one final content chunk. See
`training/patches/phase6-gate-chatml-history-fix.md`.
